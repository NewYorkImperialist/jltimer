# jlTimer UI options

All jlTimer UI options live in the normal **Options** dialog (the first button in the button bar). They are saved like every other csTimer setting: as entries in `localStorage['properties']`, registered with `kernel.regProp`. **No new storage keys** were added. (`kernel.js` `cleanLocalStorage` deletes unknown `localStorage` keys anyway.) The options persist across reloads, travel in *Export to file*, and reset with *Options → Reset*.

| Option (Options section) | Values | jlTimer default | Stored as |
|---|---|---|---|
| UI design is (ui) | Normal, Material design, … , csTimer+, **jlTimer** | jlTimer | `uidesign: 'jl'` |
| select color theme (color) | manual, style1 … solarized light, **jlTimer dark** | style1, the first scheme in About → Color schemes (same as csTimer) | `color: '1'` plus `col-*` (choosing the jlTimer dark preset applies its palette and stores `u`, so exports stay readable by csTimer) |
| select timer's font (ui) | random, normal, digital1–5, Roboto, **jlTimer sans** | digital1 (csTimer's LCD font) | `font: 'lcd'` / `'jl'` |
| Layout (ui) | **Familiar**, **Minimal** | Familiar | `jlLayout: 'c' / 'm'` |
| Virtual cube size (virtual cube) | percentage | 100 | `vrcSize` |
| Animated background (color) | Off, On, **On, pause while timing** | On, pause while timing (Off when the system asks for reduced motion) | `jlThemeAnim: 'n' / 'y' / 'p'` |
| PB celebration (ui) | Off, Single only, **Single + averages** | Single + averages | `jlPbFx: 'n' / 's' / 'a'` |

The defaults reproduce the csTimer+ design with csTimer's first color scheme and LCD digits. Colors and fonts use csTimer's own defaults, so an imported csTimer setup looks the same as on cstimer.net. A value you already saved, or imported from csTimer, is kept.

## Searching the options

The **Search settings** box at the top of the Options dialog filters every section at once. It matches, case-insensitively, the setting's label, the section name (e.g. *timer*, *color*) and, for drop-downs, the names of the choices (searching "Roboto" finds *select timer's font*, with "→ Roboto" shown next to it). Matching rows are listed flat, with the section name at the right and the matched text in bold link color. The section tabs and headers are hidden while you search. The rows are the normal option rows, not copies, so changing a setting in the results is the same as changing it in its section. **Esc** (or the × button) clears the box and brings back the normal view at the same scroll position. Press Esc again for the usual behavior. The box is cleared each time Options opens and never takes focus by itself, so the phone keyboard doesn't pop up. Keys typed in it don't reach the timer, the virtual cube or the shortcuts. Hidden internal settings (only shown with `?debug=1`) stay hidden. Code: the settings-search part of the `property` module in `src/js/kernel.js`, with `.optsrch*`/`.optgrp` styles in `src/css/style.css`.

## What each option does

- **jlTimer design** (`html.cspt.jlds`): csTimer's built-in csTimer+ design (borderless panels, system font, spaced scramble, wide button bar) plus jlTimer's own outline icons for the button bar and the scramble-options gear. jlTimer-specific styling goes in the `.jlds` rules in `src/css/style.css`, so upstream's csTimer+ CSS stays untouched. Choosing "csTimer+" gives the upstream design with the filled icon font.
- **Colors**: the default is csTimer's style1 `#000 #efc #fdd #fbb #00f #ff0 #000` (text, background, panels, buttons, links, logo, logo background), the first scheme in About → Color schemes. The **jlTimer dark** preset applies a dark slate palette `#dde #223 #334 #445 #8bf #fff #46c #fb4`. Both use the existing color-template system, so the *manual* color pickers, *import/export…* and the About color list still work.
- **jlTimer sans** (optional timer font): your OS interface font with tabular (fixed-width) digits. The running time doesn't shift sideways.
- **Layout**
  - *Minimal* keeps the scramble and the timer (and the virtual cube, if you use one). Panel frames are removed, the time list and tools panels are hidden, and the button bar fades until you hover or focus it. Panels are hidden through their **normal button states**, so the list-times and tools buttons still open them at any time.
  - *Familiar* is the classic arrangement. Switching back shows the scramble and time list again.
  - Shortcut: **Alt+L**.
- **Virtual cube size**: scales the virtual cube, and the virtual view of a bluetooth cube, relative to the timer size. It doesn't change the size of the timer digits; *timer size* still controls those. Shortcuts: **Alt+=** larger, **Alt+-** smaller, **Alt+0** back to 100%.

The shortcuts work only while the timer is idle, with no dialog open and no focus in a text field. That way they never reach the cube or the timer mid-solve. They follow the existing *use keyboard shortcut* option.

## Editing the virtual cube keys

About (click the logo) → **Virtual cube key map** tab. Click a key in the table and choose the move it should do from the menu that appears in that key. Several keys can do the same move. **none** turns a key off, and **default** restores its original move. Changed keys are underlined. **Reset keys** restores every key. The layout picker (qwerty, dvorak, colemak or a custom layout string) still decides which physical key sits in each position.

jlTimer's default key map differs from csTimer's in one key: **`,` does M** (csTimer: Uw). The choices are stored in the `vrcKeyMove` setting (`{physicalKeyCode: qwertyKeyCodeOfMove}`, with `-1` for "none", inside `properties`). They apply to every virtual puzzle, because all of them read keys through `help.getMappedCode`. The move names in the table are the 3x3 moves; on other puzzles a key does whatever that key position does there.

## Live TPS

Options → virtual cube → **Show live TPS** (off by default) shows how fast you are turning during a timed virtual solve, like WPM for typing: turn inputs (not cube rotations) per second over a short rolling window (**Live TPS window**: 0.25, 0.5 (default), 1 or 2 s), measured from when each key is pressed, not from the turn animation. It appears small, right above the "solve" text, while the timer runs and drops to 0 when nothing was pressed within the window. The solve's average TPS is still shown with the result as before.

## Free play (virtual cube)

Options → virtual cube → **Free play** (off by default), or **Alt+F** (a keyboard shortcut like Alt+L, so it follows *use keyboard shortcut*; idle only). For playing with the cube without timing: the cube resets to solved, and while the timer is idle every cube key and phone swipe turns it freely (normal animation, skins, move effects). **Space resets it to solved** (no scramble; on phones a tap outside the cube does the same, a swipe on the cube is a turn). Nothing starts the timer and nothing is recorded: no solve, no DNF, no PB celebration, no move log, and Esc does nothing, so the cloud sign-in gesture (which needs a cancelled solve) can't fire. A small theme-coloured label "free play · N moves" sits above the side timer (on phones the move count wraps to its own line); with *Show live TPS* on, live TPS shows too. Works for every virtual puzzle (NxN, 1x1x2, Square-1, Clock, Pyraminx, Skewb, Megaminx, Helicopter, FTO, Icosamate, ...): Space restores that puzzle's solved state. Turning it off rebuilds the cube solved and the next Space is a normal timed attempt. The setting (`vrcFree`) persists; after a reload in free play the cube starts solved. It only matters with the virtual (or qCube) input; other inputs ignore it.

The Icosamate (`ctico`) had no keys at all, so it could not be turned by keyboard; it now has the 3x3 key positions for its six scramble axes: I/K UR, D/E UL, J/F UrUl, H/G FlFr, W/O LBl, S/L RBr (the arrow keys turn the view).

Code: the `free*` helpers and the early branches in `onkeydown` / `moveListener` in `js/timer/virtual.js` (Space rebuilds the puzzle via `reset()`, which is solved), `vrcFree` in `js/timer.js`, Alt+F in `js/shortcut.js`, `#multiphase > aside.jlfree` in `css/style.css`, the Icosamate keys in `js/twisty/twistypoly.js`. `timer.virtual.puzzle()` returns the puzzle on screen (for checks and tests).

## Virtual cube responsiveness

- **Key-time stamps**: a virtual-cube move is recorded at the key's own `event.timeStamp` (the same performance clock as `$.now()`), not at the moment the handler gets to run, so a busy main thread no longer shifts the recorded `move@ms` times, the timer start (first turn) or the solve time (last turn). Space (scramble / inspection start) and Esc (DNF time) use it too. It falls back to the current time when the event has no usable timestamp (synthetic events, touch and drag input, very old browsers with epoch timestamps). The record format is unchanged. Code: `$.eventTime(e)` in `js/lib/utillib.js` (shared with the keyboard timer, below), used by `eventTime()` in `js/timer/virtual.js`, passed as `e.ts` to `TwistyScene.keydown` (`js/twisty/twisty.js`, `js/twisty/qcube.js`), which uses it for the moves that key adds.
- **Catch-up**: when keys come faster than the turns animate (finger-trick bursts), the waiting turns speed up so the cube shows the latest key's turn finished about one turn duration after that key, and a turn that finishes hands the rest of its frame to the next waiting turn instead of wasting it. Only the animation is shortened; every move is applied in order and none is skipped. With nothing waiting, turns run at the configured *VRC base speed* exactly as before. Code: `animationStepFor()` / `animateLoop()` in `js/twisty/twisty.js`.
- Measured (headless Chrome bench, `scratchpad/cubeperf/`): the canvas renderer costs ≤0.5 ms per frame on desktop and ≤2.2 ms at 4× CPU throttle, so there is no WebGL renderer; idle cubes don't redraw. With *Animated background: On* the petals keep redrawing a full-screen canvas during the solve, which in the bench added one or more frames of presentation latency (it varies from run to run, with or without these changes); the default (*pause while timing*) avoids it.

## Keyboard, touch and mouse timer

- The normal timer (input *Keyboard*, also *Training* `l`) takes the start and stop times from the input event's own `event.timeStamp` like the virtual cube: Space keyup (start), any stop key's keydown (stop, phases), the inspection start (Space keyup) and so the +2 / DNF inspection penalties, which are computed from those times. On phones the `#container` touchstart / touchend handlers (`js/kernel.js`) pass the touch event's timestamp into the synthetic `{which: 32}` key events, and so does the mouse timer (*useMouse*). A busy main thread (another tool computing, a slow frame) no longer shifts a recorded time; before, a 30 ms task added up to 30 ms (and could turn a 15.00 s inspection into +2). Fallback: the handler's time when the event has no usable timestamp (missing / 0, in the future, older than 1 s); times never go backwards across events. Hold-to-ready (`preTime`), the colours and everything else are unchanged. Code: `inputTime()` in `keyboardTimer` (`js/timer.js`), `$.eventTime` (`js/lib/utillib.js`).
- Checked with scripted key events of known timestamps (exact to the ms, with and without a 30 ms busy task, inspection 15000 / 15001 / 17000 / 17001 ms → OK / +2 / +2 / DNF), and real CDP key, mouse and touch (iPhone 13) input with a busy task (error 0 ms; before up to ~30 ms, and ~15 ms on emulated touch even idle).

## Time list windowing

The time list renders only the rows near the view (the view ± 40 rows); two spacer rows sized by the measured row height stand for the rest, so the scrollbar spans the whole session in both orders (newest first and *statinv*), and jumping anywhere, deleting a solve or a new solve renders about a screenful of rows. The rows are re-rendered on scroll when the view comes within 8 rows of an edge. Filter and rank sorting build the list of shown solves once (same order and filter results as before); clicking a row, PB highlighting, multi-delete, the average columns and keeping the scroll position after a delete work as before. Columns never shrink while scrolling (the title cells keep the widest width seen until the list is rebuilt). The row height is measured once and again on a resize (keeping the top row in place). On the 10.5k-solve session: jump to the bottom ~25 ms (was ~0.55 s), delete near the bottom ~65 ms (was ~0.95 s). Code: `table_ctrl` in `js/stats/stats.js`.

## PLL stats

Tools → **Reconstruct → PLL stats** (next to *cases*) shows how fast each PLL is midsolve. Every finished 3x3 solve with a move record (virtual cube or smart cube, DNFs excluded) is split into CFOP steps by csTimer's reconstruction (`recons.calcRecons`, `cf4op`) and its PLL case is identified (`cubeutil` case tables, any AUF). Nothing extra is stored: it is computed from the saved solves each time. The tools panel shows a short table (case, N, mean, TPS, weak) and **full table** opens a dialog with every column: N, share, mean, recognition (pause from the last OLL turn to the first PLL turn), execution (first to last PLL turn, AUFs included), execution TPS, σ, weakness score, turns, slips, best and the mean of the last 5/12/25/50 solves of the case. Click a header to sort. The scope is this session, all sessions, or all sessions but the trainer's drill session. The 3 slowest cases by mean are tagged #1-#3. A PLL skip (also one that needed only an AUF, which then stays in the OLL step) is its own row, counted in N and share but not in the times. **CSV** downloads one row per solve. **drill weakest N** opens the PLL trainer (below). Code: `js/stats/algstat.js`; its `STEPS` table holds one entry per step (PLL, OLL), each with its own tool. The first open of a cold session reconstructs every solve in 30 ms slices with a small progress bar (*reconstructing i / n*), waiting while the timer runs, is about to start or inspects; the reconstructions are cached by stats (`recons_cf4op`) and shared with OLL / COLL stats and the dashboard (current session, non-DNF solves), so whichever opens first does the work and the others open in about 0.1 s. Results are identical to the unsliced computation.

**slips** (PLL and OLL stats, full table): the share of a case's executions that took 4 or more moves over your median for that case, then the mean extra moves of those (e.g. `16% +8.2`). It catches a typo mid-alg and its repair. Moves are counted as executed, not in HTM: every input turn counts, so a typo and its undo (R R') are 2 moves where HTM would merge them; a slice is 1; rotations are not counted. Turns of the last-layer face at the very start and end of the step (pre- and post-AUF) are left out, so an AUF never looks like a slip (`mvc` in the per-solve record, from the step's effective moves `data[k][6]`). A case needs 5 solves for its median. The summary line shows the overall slip rate; a case at 1.25× that rate or more is bold. Hover a row for the usual move count, the number of slips and how much slower they were than the other executions. The CSV has a `movesNoAUF` column. On the user's session 3 (10.5k solves) U/J/T perms slip in about 18% of executions (offline estimate ~16%), at about 2 s each.

## OLL stats

Tools → **Reconstruct → OLL stats** is the same table for the 57 OLLs, from the same reconstructions (the OLL step: from the last F2L turn to the turn that orients the last layer). Recognition is the pause from the last F2L turn to the first OLL turn; a U turn before the alg counts as a pre-AUF (in exec and turns; hover a row for its rate). An **OLL skip** (last layer already oriented when F2L is done) is its own row. Two additions:

- **edges at OLL**: how many last-layer edges were already oriented when the OLL started: all four (an OLL skip counts here), two (line or L; hover for the split) or none (a dot case), next to the chance with random edges (12.5 / 75 / 12.5%; line 25%, L 50%). With F2L that influences edges, "all" is far above 12.5%.
- **families**: a list next to the scope shows only one family. The family is the first part of csTimer's case name (Point = dot, Square, SLBS = small lightning, Fish, Knight, CO = corners oriented, OCLL = edges oriented, Awkward, P, T, C, W, BLBS = big lightning, L, I).

The OLL view keeps its own settings (`ollStatScope`, `ollStatSort`, `ollStatDir`, `ollStatRecent`, `ollStatFam`), so sorting one table doesn't change the other. Both views share one reconstruction per solve, so opening the second is quick (on a 10.5k-solve session the first one takes about 1 s, the second about 0.1 s). **drill weakest N** opens the OLL trainer.

## COLL / ZBLL stats

Tools → **Reconstruct → COLL / ZBLL stats** (`js/stats/collstat.js`). A CFOP solve has no COLL or ZBLL step: such an alg shows up as an **OCLL** (an OLL with all last-layer edges oriented, csTimer's OCLL-21…27) whose OLL step also solves the corners (the PLL left is Ua, Ub, H, Z or a skip) or everything (a PLL skip). The tool pairs each solve's OLL and PLL records from *PLL / OLL stats* and identifies the **COLL case** from the cube at the start of the OLL step (csTimer's COLL table, `cubeutil.getIdentData('COLL')`, any AUF; 40 cases in 7 shapes). That cube is the inverse of the OLL step and every later step (the solve ends solved); the OLL step's own transform is not enough, as its corner permutation is that of the alg done, not of the cube.

- **By shape** (H, Pi, U/headlights, T, L/bowtie, Sune, Antisune): N, **COLL** = share with the corners solved after the OLL step (chance with a plain OCLL alg: 1/6, since 4 of the 24 corner orders are solved up to AUF; bold from 75%), mean OLL time with (c) and without (o) the corners solved, mean OLL + PLL time the same way, **gain** (LL o − LL c, 5+ solves each way), **LL skip** with the number expected by chance in brackets, **ZBLL≈**.
- **By COLL case** (dialog, filter by shape): N, COLL rate, OLL / LL times, LL skips, ZBLL≈. Cases you know show ~100%, cases you don't ~0% (the corners then end solved only when the alg you did is that case's COLL, e.g. Sune on S-1).
- **ZBLLs**: one solve cannot tell a ZBLL from a lucky skip, but a case can. After a COLL the edges are random, so 1 in 12 solves skips the PLL; each ZBLL of a case you know turns another 1/12 of its solves into skips. **ZBLL≈** = (skips above chance) / (N / 12), counted only when the skips are more than 2σ + 1 above chance; the shape row sums its cases. A list of the latest 15 LL skips after an OCLL shows the case, OLL time, moves against your usual alg for the case (*other alg* when 4+ moves away; a ZBLL is often as long as the COLL alg, so this alone misses most) and a *replay* link.
- A takeaway line: which shapes you solve the corners on, the LL time with vs without the corners solved per shape, the skips against chance and the estimated ZBLLs.

On the user's session 3: OCLL in 42% of solves; corners solved H 100%, Pi 100%, U 98%, L 98%, T 79% (T-3 0%, T-6 71%), Sune 19%, Antisune 17% (chance); 386 LL skips after an OCLL against 264 by chance, pointing to about 11 known ZBLLs (T-4 3, T-6 3, U-2 3, L-6 1). Note: the data says full bowtie and partial T, the reverse of the offline notes. Scope: this session or all sessions (`collStatScope`, `collStatShape`). The work runs in 25 ms slices with a progress count (10.5k solves cold: about 1.4 s, longest main-thread gap under 100 ms) and waits while the timer runs.

## PLL and OLL trainers

Tools → **Reconstruct → PLL trainer** and **OLL trainer** drill the weakest cases on the virtual cube (`js/tools/algtrainer.js`, one trainer per step from the same code). Each lists every case with its N, mean and weakness score from the real solves (all sessions but the drill one), its chance in the drill and its mean in the drill session.

- **start drill** switches to the trainer's own session ("PLL drill" / "OLL drill", created on first use) with csTimer's `pll` / `oll` training scrambles; **stop** goes back to the previous session and scramble filter. Only one drill runs at a time: starting one stops the other. Leaving the drill session by hand ends the drill.
- Modes: **weakest N** (PLL 3/5/7/10, OLL 3/5/10/15; equal chances), **weighted** (every case, weight e^score clamped to ±1.5) and **pick** (click rows; in the OLL trainer the cases are grouped by family, and a family row picks or unpicks the whole family). The case filter values are weights (`scrMgr.rndState`; the OLL skip is never drilled).
- **random y** turns the whole cube by a random y at each setup. **show alg** reveals the case image, its name and a common alg (the 57 OLL algs are checked by the tests to set up their case).
- The time runs from Space (case shown) to the last turn, so it is recognition + execution, split as in the stats.
- **OLL completion**: an OLL attempt ends as soon as the last layer is oriented with the F2L of the setup intact, whatever the AUF or permutation, so finishing the whole last layer counts too. The check replays the scramble and the attempt's moves on a cubie model in the scramble's own frame (`isDone`, called from `timer/virtual.js`), so a state that only looks oriented on another axis doesn't end the attempt. Algs with f/f' (typed as F + S, the key map has no Fw) are counted whole: for trainer solves the stats keep everything up to the end of the attempt in the OLL step.

Settings: `pllDr*` and `ollDr*` (mode, N, picks, random y, drill session, previous session and filter, on/off), saved like other options.

## Analysis dashboard

Tools → **Reconstruct → analysis** → *open analysis* opens a large dialog that recreates the useful parts of an offline analysis report, computed live from your solves. Nothing is computed on page load or by the tools panel; work starts only when the dialog opens.

- **Scope**: *this session* or *all sessions* (every session with the current session's scramble type, merged by date). **Range**: last 100 / 500 / 1000 / 5000 solves, last 7 / 30 / 90 / 365 days, or all. Both are remembered as ordinary properties (`jlDashScope`, `jlDashRange`).
- **Overview**: solves (and how many have a move record), mean / median, σ, DNF rate, best single / ao5 / ao12 / ao100 in the range (csTimer's `TimeStat`, same trimming as the session stats), TPS overall and while turning, pause share, rotations per solve.
- **Progress**: rolling ao100 (ao12 / ao5 for short ranges) with a dashed best-so-far line, inline SVG.
- **Steps**: CFOP cross, F2L 1-4, OLL, PLL: recognition, execution, time (bar), turns, execution TPS, pause, rotations, and the difference against all solves in the scope (or last 100 vs all when the range is everything).
- **Last layer**: OLL / PLL / LL skip rates and last-layer edge orientation at OLL against chance, slowest 5 OLL and PLL cases, link to *PLL stats*.
- **Consistency**: histogram of times with the median, σ per block of 100 solves (fastest and slowest 5% of each block left out so one forgotten timer does not dominate).
- **Slowest solves**: top 10 with the step that lost the most time against its mean; *replay* opens csTimer's replay of that solve (the dashboard closes; reopening it is instant).
- **Chokes** (*PLL* / *OLL* toggle, `jlDashChoke`): solves on a great pace into the step that the step ruined. Pace = final − step time + your median step time for that case (medians over the range; a case needs 5 solves). A choke has pace under the threshold and a step time at least 1.5 s over the case median (1.0 s when the pace was 0.5 s better still). The threshold is your fastest 5% of the times shown (5th percentile), stated in the takeaway. Table (newest 30): solve #, date, final, pace, case, step time (usual), lost, turns (usual), *replay*. The takeaway gives the count, the share of great-pace solves lost (a skip on a great pace counts as great, never as a choke) and the most choked cases. Session 3: threshold 12.07 s, 43 PLL chokes of 485 great-pace solves (Ub 8, Ua 7, T 7); at the offline threshold of 11.5 s it finds exactly the offline 21 chokes of 242 (offline 243), mostly Ua/Ub/Jb/T (`jlDash.chokesAt(ms, step)`).

Each section starts with a one-line takeaway computed from the numbers.

**How it is computed.** Solves with a move record (virtual or smart cube, 3x3) are split by csTimer's own reconstruction (`recons.calcRecons(times, 'cf4op')`) and their OLL / PLL cases identified with `cubeutil.getIdentData`. From the move timestamps: a **pause** is a gap of 300 ms or more between two inputs; turning time is the rest; rotations made at 0 ms (inspection) are ignored and other x / y / z rotations are counted separately, never as turns. TPS = turns / solve time (ratio of sums). A PLL skip includes "only an AUF was left" (chance 1/72; 1/288 with no AUF at all; LL skip 1/15552), as in *PLL stats*. (Earlier versions said 1/18 and 1/3888, which was wrong: 4 of the 288 last-layer permutations are solved up to AUF.)

**Performance.** About 0.1 ms per solve: the user's 10.5k-solve session takes about 1.4 s cold, in 25 ms slices with a progress bar (longest main-thread gap about 45 ms), and waits while the timer runs. Per-solve results stay in memory for the page's lifetime, keyed by session, date, move-record length and time, so reopening takes a few tens of ms and a new solve adds only its own work. No storage keys, no IndexedDB changes. Code: `js/stats/dashboard.js`, `.jld*` styles in `css/style.css`.

## Annotated replay

The virtual replay (the *Review* / turns link under a solve, the solve detail dialog, and *replay* in the analysis dashboard) has a timeline strip under the slider and a short table under the controls. It is display-only and computed when the dialog opens; nothing is stored.

- **Step bar** (3x3 solves that end solved): one segment per CFOP step (cross, f2l-1 to f2l-4, oll, pll) from csTimer's reconstruction (`recons.calcRecons(..., 'cf4op')`), placed by time. The hatched part of a segment is recognition (last turn of the previous step to the first turn of this one), the solid part is execution. The label shrinks to fit: "pll Ub 30 mv 10.7s", "pll Ub 10.7s", "Ub", "pll", "p"; hover a segment for the full text. OLL and PLL segments carry the case name (`cubeutil.getIdentData`, as in *PLL / OLL stats*). Click a segment to jump to the start of that step (the cube as it was after the previous step's last turn); the next turn from there is the step's first turn. A dark line marks the current position.
- **Pauses**: under the bar, every gap of 300 ms or more between two inputs (rotations count as inputs); gaps of 1 s or more are taller and darker. Hover for the length.
- **Slips**: a turn immediately undone by the next one (R R', U2 U2), usually a mistyped key. The pair is marked with a small triangle above the bar (warning color) and both turns are shown in that color in the move list on the right. Orientation moves recorded at 0 ms are not counted.
- **Summary table**: step, recognition, execution, turns, TPS (turns / step time, as in the *step* tool) and **vs avg**: the step time (recognition + execution) against its mean over the latest 100 solves of the current session that have a reconstruction (shown when at least 5 do). The step that lost the most is in the warning color. Click a row to jump like a segment. A skipped step shows as "skip". Under it: number and total of pauses (and how many are 1 s or longer) and the number of slips.
- **Other puzzles and other cases**: for any other puzzle, a DNF, or moves that do not solve the scramble, there is no step bar or table; the pauses and slips are still shown on a plain track. The image tool's scramble replay shows no annotations. The solve detail dialog and the timer pass the DNF flag, so a solve whose saved scramble doesn't match its moves (seen in some old imported data) still gets its steps from there; other callers check that the moves solve the scramble.
- The replay dialog is larger than before (class `dialogreplay`) and sizes the cube to the space left by the bar and table; at phone width the whole dialog fits without sideways scrolling.

Code: `js/twisty/twistyreplay.js`, `.rpl-*` styles in `css/style.css`.

## Move effects

Options → virtual cube → **Move effect** adds an arcade-style flourish whenever a layer of the virtual cube turns (default **None**). There are 12: Arcade Combo, Comet Orbit, Fever Mode, RGB Glitch, Ink Splash, Lightning, Neon Trail, Zen Ripple, Crystal Shards, Shockwave, Blade Slash and Spark Burst. Each also has a finale when a timed solve ends. They draw on a transparent canvas over the cube that ignores the mouse, they stay on the face edges or outside the cube so stickers remain readable, and they shrink to a short outline flash when the system asks for reduced motion. The moves of a scramble don't trigger them.

The layer highlights draw on the layer that turned instead of around the cube, chess.com style: the layer's stickers get a glowing rim and a trail slides along the layer in the turn direction. There are 7: Teal Glow (chess.com style), Squiggle Trail, Tron Lightcycle, Synthwave Sweep, Motion Streaks, 8-Bit Trail and Neon Pulse. Fills over stickers stay faint and fade within about 250 ms so colours stay readable. A v1 and a v2 effect can run together. v2 effects use `api.layer(ev)` (the turning slab's strips, cap and belt path) and register with `v2: true`.

All styles are in one list, **Move effect** (Column Glow first, then the layer highlights, then the original effects; older separate v2/v3 choices are carried over). Column Glow: the whole visible part of the turning layer glows see-through blue while it turns (driven by the turn's live progress). **Column Glow hold** keeps it lit after the layer lands (turn only, 200 ms fade, 400 ms fade or until the next move) and **Column Glow strength** picks normal, strong or bright. The hold times are real time.

**Effect duration** (1x, 1.5x default, 2x, 3x) slows every v1 and v2 effect evenly so they stay visible at fast turn speeds; effects read time through `jlFx.now()` and the `t`/`dt` passed to `api.add`.

The framework is `src/js/fx.js` (API documented at the top of that file). Each effect is one file in `src/js/fx/`, concatenated into the separate async bundle `js/jlfx.js`.

## Virtual cube skins

Options → color, right under **Cube** (the six cube colours):

- **Cube skin** (default **Standard**): Standard, Pastel, Sakura (butter, blossom pink, plum, white, deep rose, matcha), Night (jewel tones), Katana (gold, sakura pink, lacquer black, ivory, crimson, steel), High contrast (white/grey/charcoal plus yellow, red, blue), or Custom. A preset simply writes its six colours into **Cube**, so the colour pickers, the 2D qCube, the scramble image and the move effects all follow; editing any colour by hand switches the skin to Custom, and colours that equal a preset select it. Every preset keeps the six faces apart for normal vision and for protan/deutan/tritan simulations (min CIEDE2000 between two faces 11 or more under simulation; Standard itself drops to about 4 for orange/green with deuteranopia).
- **Sticker style** (default **Classic**): Classic is the csTimer look (floating stickers, thin black outline). Stickerless: coloured pieces that fill the cubie, slightly rounded, with a hairline dark core between them. Glossy: rounded stickers on black with a soft highlight in the corner nearest the top-left of the screen. Soft: well-rounded stickers on a plum body (white body with the Sakura colours). The non-classic styles also shade faces turned away from a fixed light a little.
- **Cube body** (default **Auto**): Auto picks the style's body (Classic: none, so nothing changes), or Black, White (warm white with faint cubie seams), Plum, or Theme (the theme's text colour). Classic + a body gives black-plastic-with-stickers.
- **Cube preview**: a small isometric cube drawn with the same rules (white top, green front, red right, like the virtual cube's start) plus the six swatches.

Changes apply immediately to every 3D NxN cube on screen (main cube, replay) without resetting it. 2x2 to 11x11 use the styles; pyraminx, skewb, megaminx etc. keep their own colours and the classic look; heli/redi/dino take the colours but not the styles.

How it works: `src/js/cubeskin.js` holds the presets and props and exposes `jlCubeSkin.style()`. `twisty/twistynnn.js` gives every sticker a second, hidden 2x2 plane behind it (the body) and `applySkin()` updates the shared materials in place (sticker scale, border, body visibility), so a change costs nothing per frame. The canvas renderer (`lib/threemin.js`, `jlSkinQuad`) reads three optional material fields: `jlRound` (rounded quad path with bezier corners), `jlShade` (16 precomputed fill colours per material, picked by the face normal) and `jlSheen` (one extra translucent fill). Frame cost while turning at 40 tps: about 0.55 ms mean per animation frame for Classic and 0.7 ms for Glossy with 4x CPU throttling, 60 fps either way.

## 1x1x2 (a real puzzle)

csTimer's "1x1x2" was a joke under Jokes that printed strings of R. In jlTimer it is a proper event: scramble type **Jokes → 1x1x2** (still listed under Jokes, now a real playable puzzle). The id stays `112`, so old sessions and exports keep working (their old R-string scrambles are still listed and still draw; R on an upright 1x1x2 just turns the whole puzzle).

- **Puzzle**: two 1x1x1 cubies stacked (2 tall, 1 wide, 1 deep), one cut, the cube colours (**Cube** / cube skin). The state is the turn of the top cubie against the bottom one (4 states); solved = aligned, in any whole-puzzle orientation, including lying on its side.
- **Scramble**: random state. One of the three unsolved states, uniformly (never solved), written as its shortest sequence: `U`, `U2` or `U'`. No orientation suffix (csTimer's random-state cube scrambles don't add one). Pre-scramble rotations (Options → Pre-scramble) are used only if they leave the puzzle upright (`z2`, `x2`, `y`...); one that tips it over is ignored, as the scramble would otherwise just turn the whole puzzle.
- **Scramble image**: a cross net, U on top, L F R B as 1x2 strips (top cubie above bottom), D under F.
- **Virtual puzzle** (input "virtual"): drawn in 3D exactly like a 2x2 (same cubie size, camera and floating double-sided stickers, so in Classic the L / R / B / D stickers peek past the front and top as on the 2x2; skins with a body hide them, as on the 2x2), with turn animation, cube skins (sticker style, body; with a body the faces at the cut are body-coloured while the top turns), camera arrows and the move-effect sticker tint. The 2D view (qCube) has no 1x1x2, so it shows the 3D one. Keys are the 3x3 map: `j`/`f` U/U', `s`/`l` D/D', `i`/`k` R/R', `d`/`e` L/L', `h`/`g` F/F', `w`/`o` B/B', `t`/`y` x, `b`/`n` x', `;`/`a` y/y', `p`/`q` z/z'; wide keys (`u`, `r`, `m`, `v`, `z`, `c`, `/`) are the matching rotation, slices do nothing. Touch/mouse dragging uses the same 3x3 board (labels show what each swipe does).
- **Rotations**: x and z lay the puzzle on its side; then the turns are the face turns along its long axis (F/B or R/L). A face turn whose layer would be the whole puzzle (R while upright, U while lying down) is what it is in the hand, a whole-puzzle turn, and is entered and logged as that rotation (`x`, not `R`), so it doesn't count as a move. This is decided on the queued state, so fast input during an animation is read correctly.
- **Timing**: a solve is recognising the state plus one turn, so timed from the first turn every solve would be 0.00. The clock runs from the moment Space shows the scramble until the solving turn's key press (key-event time, like every jlTimer virtual time); inspection is skipped for this event. Move log `move@ms` (rotations included), move count = turns of top against bottom (`U U` counts once, like the NxN). Replay plays it back (no CFOP annotations; auto-ori is off for it).

How it works: `src/js/lib/puzzle112.js` is the model (integer sticker positions/normals; which cubies a move turns, relative state, notation, scrambler) shared by the scrambler (`scramble/utilscramble.js`), the image (`tools/image.js`) and the virtual puzzle `twisty/twisty112.js` (twisty type `112`, registered in `$.TWISTY_RE`, colours/skins via `puzzleFactory`). The start-on-Space path is in `timer/virtual.js` (`startSolve`).

## 1x1x1 (a joke you can play)

csTimer's "1x1x1" under **Jokes → 1x1x1** printed a string of random rotations and had no virtual puzzle. In jlTimer it is playable in the virtual timer, still under Jokes and still a joke: **any move solves it**. Press Space, the scramble is applied and the clock starts; the first key (or swipe) turns the cube and stops the clock, whatever orientation it ends in.

- **Puzzle**: one cubie with the cube colours (**Cube** / cube skin), drawn like the 2x2 and the 1x1x2 and the same overall size as the 2x2: floating Classic stickers are double-sided so the back stickers peek through the gaps; skins with a body hide them.
- **Scramble**: unchanged, csTimer's random string of `x`, `y`, `z` rotations (length 25), so old sessions (id `111`) and their scrambles are untouched. Pre-scramble rotations are ignored for it. The scramble image is a cross net of single cells (U, then L F R B, then D), drawn for old scrambles too.
- **Moves**: every turn on a 1x1x1 is a whole-cube rotation, so every key of the 3x3 map rotates it: R/L keys are `x`/`x'`, U/D are `y`/`y'`, F/B are `z`/`z'`, wide keys and the x/y/z keys are their rotations. They are logged as those rotations (`y@751`), as on the 1x1x2. Touch/mouse swipes use the 3x3 board the same way. Slice keys do nothing.
- **Timing**: as the 1x1x2: from the Space press (scramble shown) to the key press of the first move (key-event time); inspection is skipped. The move count is 1 (rotations are the only moves a 1x1x1 has). Replay, solve detail, export/import, turn animation, cube skins and the move-effect sticker tint (not used: every move is a rotation) work as for the 1x1x2.

How it works: the 1x1x2 code is parameterised by height. `lib/puzzle112.js` `solved(1)` is one cubie at the origin with six stickers; `layerOf` then always returns the whole puzzle, so every face turn resolves to its rotation. `twisty/twisty112.js` registers twisty type `111` as `create112Twisty(..., 1)`; its `isSolved` reports solved once a move has been made since the scramble (the move counter `scrambleIt` clears). `tools/image.js` draws the net with height 1, and `timer/virtual.js` uses the 1x1x2's start-on-Space path for both.

## Floppy Cube (virtual 3x3x1)

Scramble type **Other → LxMxN → 1x3x3 (Floppy Cube)**, id `133` as in csTimer, so old sessions and exports load as they are.

- **Puzzle**: the flat 3x3x1: a fixed centre, 4 edges, 4 corners, cube colours (**Cube** / cube skin; U and D are the big faces). The four sides R, F, L, B turn **half turns only**, as on the real puzzle: a half turn swaps the side's two corners and flips its edge (192 positions). Solved = every piece home, in any whole-puzzle orientation (upside down or standing on a side too).
- **Scramble**: csTimer's random-state scrambler (unchanged, uniform over the 191 unsolved positions, optimal: at most 8 turns, the Floppy's God's number). jlTimer writes its half turns as `R2 L2 F2 B2` instead of csTimer's bare `R L F B`, which reads like quarter turns to a cuber. Old scrambles without the `2` still apply and draw the same: on the Floppy any turn of a side (`R`, `R'`, `R2`) is its half turn.
- **Scramble image**: a cube net of the flat puzzle: U (3x3) on top, the L F R B sides as 3x1 strips below it, D (3x3) under F.
- **Virtual puzzle** (input "virtual"): drawn in 3D the size of a 3x3, with turn animation, cube skins (sticker style, body; the faces a turn uncovers show the body, in Classic a dark sticker-sized tile), camera arrows, the move-effect sticker tint and the 2x2's double-sided Classic stickers, so the stickers below and behind peek through the gaps. The 2D view (qCube) has no Floppy, so it shows the 3D one. Keys are the 3x3 map: `i`/`k` R, `d`/`e` L, `h`/`g` F, `w`/`o` B; both keys of a side turn its half turn (logged `R2`). `j`/`f` (U) and `s`/`l` (D) turn the big faces, which is the whole puzzle turning: entered and logged as `y` / `y'`. `t`/`y` x, `b`/`n` x', `;`/`a` y/y', `p`/`q` z/z'; wide keys are the matching rotation, slices do nothing. After `x` or `z` the puzzle stands on a side and the turnable sides follow it (e.g. after `x` the old F side is on top and `j` turns it). Touch/mouse dragging uses the 3x3 board, with the labels showing what each swipe does.
- **Timing**: normal: inspection if enabled (rotations don't end it), the clock starts on the first side turn and stops when solved. Move log `move@ms` with rotations, move count = side turns (`R R` counts once). Replay plays it back in the orientation it was solved in (no auto-ori, no CFOP annotations).

How it works: `src/js/lib/puzzlefloppy.js` is the model (every piece a cubie at an integer position with an integer orientation; which pieces a move turns, the big-face rule, half turns, solved, notation), shared by the scramble image (`tools/image.js`) and the virtual puzzle `twisty/twistyfloppy.js` (twisty type `133`, registered in `$.TWISTY_RE` from the model file, colours/skins via `puzzleFactory`). The renderer draws all six faces of every cubie and shows a face only while nothing sits against it, so a turn uncovers exactly the faces it should.

## Super Floppy (virtual, random state)

Scramble type **Super Floppy → random state**, id `sfl` as in csTimer (whose entry had no name and printed random R L U D turns), so old sessions and exports load as they are.

- **Puzzle**: Katsuhiko Okamoto's shape-shifting Floppy that also turns quarter turns. The 4 edges stay put and rotate (4 orientations each); the 4 corners move among 12 locations: the 4 flat ones plus one above and one below each side's edge. A quarter turn of a side cycles its 4 locations (flat, above, flat, below), so its corners swing out of the plane or back into it; a side can hold 0 to 4 corners. 3,041,280 states. Solved = flat, every corner home, every edge unturned, in any whole-puzzle orientation.
- **Rules** (Options → scramble → **Super Floppy rules**, prop `sflMode`, default **official**): the official puzzle locks a side whose 4 locations hold no corner (the bare edge can't turn); imitations let it turn. The setting is used by the scrambler and by the virtual puzzle, where a locked turn is refused with a short shake of the puzzle (a fade with reduced motion) and is not entered: not logged, not counted, it doesn't start the timer.
- **Scramble**: random state: a uniform random unsolved state, written as the inverse of an optimal solution in R F L B with `'` and `2` (a half turn counts as one move). Official scrambles never turn a locked side (also not halfway through a half turn), so they work on every Super Floppy; imitation scrambles may turn bare edges and are a little shorter. Optimal means never longer than God's number: 15 official, 13 imitation. Verified against Jaap Scherphuis's analysis (jaapsch.net/puzzles/floppy2.htm): a breadth-first search over all states gives exactly his distance tables, maximum 15 / 13, averages 9.8558 / 9.0040, and the 495 corner arrangements make his 72 shapes up to the puzzle's rotations (45 with mirror images). Changing the rules makes a new scramble.
- **Old scrambles**: csTimer's old R L U D scrambles were for the puzzle held upright (big faces front and back). jlTimer applies them laid flat, U as B and D as F (`R U' L D2` = `R B' L F2`), in the scramble image too, and without the lock (they ignored it; every state can still be solved under official rules).
- **Scramble image**: the Floppy's cube net with three-row sides: each side view shows that side's layer, a plus of the edge, the two flat corner locations and the locations above and below the edge (empty ones left out, faces without a sticker grey); the U / D views show what is seen from above / below, a corner standing out towards the viewer marked with a diamond.
- **Virtual puzzle**: the Floppy's renderer (3D, skins, peek-through, touch board, camera arrows; the arrow keys show the corners standing up best) with quarter turns: `i`/`k` R/R', `d`/`e` L/L', `h`/`g` F/F', `w`/`o` B/B'; U/D keys and rotations as on the Floppy. A face without a sticker (a corner's inner side, an edge face next to an empty location) is drawn as the body; in Classic, which has no body, as a dark sticker-sized tile, so the shape reads the same in every style. Timing as usual (inspection, clock from the first turn), move count = side turns (`R R` counts once), replay.

How it works: the geometry is the Floppy's (`lib/puzzlefloppy.js`: corners standing out are just pieces at (+-1, +-1, 0) / (0, +-1, +-1); `isLegal` is the lock). The scrambler `scramble/superfloppy.js` uses an abstract model (corner locations x edge orientations, one integer per state) and IDA* with two exact pruning tables of corner locations x the orientations of two edges (an adjacent and an opposite pair, used for all six pairs through the puzzle's 4-fold symmetry), 2 x 332 KB per rules set, built in about 40 ms on the first scramble of that rules set (later ones take about 0.02 ms). The menu id stays `sfl`; `scramble/scramble.js` maps it to the scrambler `sfli` when the setting is imitation (as 444wca maps to 444m), so the worker's cached scrambles always follow the setting.

## 15 puzzle and 8 puzzle (virtual)

The scramble types **Other → 15 puzzle** and **Other → 8 puzzle** (csTimer's ids, unchanged: `15prp` / `15prap` / `15prmp` random state, `15p` / `15pat` / `15pm` random move, `8prp` / `8prap` / `8prmp`) are playable in the virtual timer (input "virtual" or the 2D view; both show the same flat grid).

- **Notation** (csTimer's, as the scramble image draws it): in **URLD** and **arrow** scrambles the letter is the direction a tile slides (`R` = a tile moves right, so the blank moves left); in **Blank** scrambles it is the direction the blank moves (`R` = the blank moves right). A count repeats the move (`R3`). Random-state scrambles are csTimer's three-stage solver run backwards from a uniformly random solvable position; random-move ones are 80 single moves.
- **Puzzle**: a 4x4 / 3x3 grid of numbered tiles drawn in the theme colours; solved = 1..15 (1..8) in reading order, blank bottom-right. **Sliding puzzle colours**: *theme* (default), *by row* or *fringe* (the scramble image's scheme), both using the **15 Puzzle** colours.
- **Keys**: arrow keys, `W A S D` and `I J K L` (up, left, down, right). **Sliding puzzle keys move**: *the tiles* (default, the usual speedsolving convention: Left slides the tile right of the blank to the left) or *the blank*. A key with nothing to slide does nothing.
- **Mouse / touch**: click or tap a tile in the blank's row or column to slide it and every tile between (one move of n tiles, logged as e.g. `L3`); on a touch screen swipe to slide tiles that way (swiping a tile towards the blank pushes the tiles between too; a long swipe keeps sliding, one tile length per move). Mouse moves act on the press.
- **Timing**: as the cube: inspection as set, the first slide starts the clock, solved stops it (key-event times). Move log `move@ms` in the scramble's own notation (Blank letters for Blank scrambles, arrows for arrow scrambles), so the replay plays it back. The recorded move count is single-tile moves (STM, `L3` = 3); the replay summary shows both STM and multi-tile moves (MTM: a run of slides in one direction is one move).
- **Animation**: each slide is drawn in about 70 ms; the model changes at once, so fast input never waits, and a tile moved again mid-slide carries on from where it is drawn. Off with the instant turn speed or prefers-reduced-motion.

How it works: `src/js/lib/puzzleslide.js` is the model and notation; `src/js/twisty/twistyslide.js` is a 2D-canvas scene with the twisty-scene interface (`twistyjs.slide`), picked by `puzzleFactory` for puzzle ids `15p` / `15b` / `8p` / `8b` (in `$.TWISTY_RE`). The scrambler and the scramble image are csTimer's (`scramble/slide.js`, `scramble/utilscramble.js`, `tools/image.js` `sldImage`).

## Mirror Blocks (virtual)

Scramble type **Other → LxMxN → Mirror Blocks**, id `mrbl` as in csTimer, so old sessions and exports load as they are.

- **Puzzle**: Hidetoshi Takeji's Mirror Blocks (Bump Cube): a 3x3 mechanism whose outer layers have different thicknesses, all faces one colour, so a scramble shows as a change of shape and solved means the cube shape is back. Layer thicknesses (in 3x3 cubies; the middle layers are 1): U 0.55 / D 1.45, R 0.85 / L 1.15, F 0.7 / B 1.3, the same offsets (0.45, 0.15, 0.3) csTimer's Mirror Blocks scramble image uses; with a different offset on each axis every corner and edge has its own shape, as on the real puzzle. Solved = every corner and edge home, in any whole-puzzle orientation; centres can be turned any way (invisible, and the 3x3 check ignores them), so every state that looks solved counts.
- **Scramble**: csTimer's 3x3 random-state scrambler (unchanged; the scramble type is an alias of `333`). Scramble image: csTimer's (stickers drawn with the pieces' sizes).
- **Virtual puzzle** (input "virtual"; the 2D view shows it in 3D too): every piece is drawn as a box; the faces that are outside on the solved cube carry the metal stickers, the sides a turn uncovers are dark plastic, and every face is shaded by its direction, so the bumps read at a glance. **Mirror Blocks colour** (virtual cube options, prop `vrcMirror`): *gold* (default) or *silver*. The cube skin's sticker style applies (size, rounding, sheen, border); its body is used when it is dark, otherwise dark plastic. Turning shows the shape shifting: the faces on the cut a layer turns against are drawn whole during the turn. The puzzle turns about its own centre for x / y / z (the mechanism sits off centre). Keys, touch board, move log, move count, replay and free play are the 3x3's (twisty/twistynnn.js), with 3x3 notation; one phase (no CFOP split).

How it works: `twisty/twistymirror.js` registers twisty type `mrbl`, which builds the NxN 3x3 (`twistyjs.createCubeTwisty`, exported by `twisty/twistynnn.js`) and re-lays its stickers: each sticker and its body plane are placed on the outer face of its cubie at the Mirror Blocks size, and each cubie gets body-coloured planes for its inner faces, carried by one of its stickers. After every move the part of each inner face that no neighbour covers is recomputed (rectangle minus rectangle, at most two pieces); the moves themselves, the facelets and the solved check stay the NxN's.

## PB celebration

When a new solve sets a new **session best** (the same bests csTimer marks in the time list: single, and the two averages of the time list, ao5 and ao12 by default), a short celebration animation (about 2.5 s) plays over the page, with a "NEW BEST / ao5 12.47" title next to the time for about 1.5 s. While the celebration is enabled, csTimer's own scrolling "Session best …!" logo hint is dropped for solves that get the celebration. It is still shown when the option is Off, or for a best the option doesn't celebrate. If one solve sets several bests, the label names the biggest one (the longest average). Option **PB celebration** (ui section): *Off*, *Single only*, *Single + averages* (default). The UI deliberately doesn't describe or preview the animation, so the first one is a surprise.

- **When it plays.** Only for a new solve from any timer (keyboard, touch, virtual cube, bluetooth, typed in), via stats.js's `timestd` signal. Editing a penalty, deleting, importing or switching sessions never plays it. DNFs never count. Not for the first solves of a session: a single needs at least 5 solves in the session and an improvement over an earlier best; an average of n needs at least 2n solves and an improvement over an earlier average.
- **Timing safety.** It never delays the next solve. Any key press (auto-repeat ignored), touch or pointer press, or the timer leaving idle (ready, inspection, running) stops drawing at once. The overlay then fades out in 0.12 s with a CSS transition, with no more script work. The overlay is a fixed full-window canvas with `pointer-events: none` (z-index 45: above the panels, below dialogs) and never takes keys. It is hidden (`display: none`) when idle. The detection runs after the time is saved, and the animation starts in the next task, so the timer finishes handling the stop first.
- **Reduced motion** (`prefers-reduced-motion`): only the label fades in, with a few petals falling gently.
- **Testing.** `jlPbFx.preview()` plays it from the console. With `?debug=1`, a *preview* link appears next to the option. `jlPbFx.newBests()` returns the bests the newest solve just set.
- Code: `src/js/pbfx.js` (detection, drawing; sprites are pre-rendered once per size), `.jlpb*` styles in `src/css/style.css`. Detection reads csTimer's own `TimeStat` for the time list (`stats.getTimesStatsList()._bestAvg`), so it always agrees with the PB highlighting.

The button bar buttons can be focused with Tab, and **Enter** or **Space** activates the focused button. ## Session manager

Click **Session** in the time list header to open the session manager. jlTimer adds three things to csTimer's table:

- **Drag to reorder**: drag a session by the **⠿** handle at the left of its row and drop it where the line appears. It works with a mouse, a finger or a pen (pointer events). Near the top or bottom edge of the dialog the list scrolls.
- **Move to top / Move to bottom**: in each row's **...** menu, next to the ↑/↓ arrows. The first session has no *Move to top* and the last no *Move to bottom*.
- **Filter sessions**: the box above the table shows only the sessions whose name contains the text, ignoring case. **X** next to it clears it, and it is cleared each time the dialog opens. While filtering, the name/scramble grouping is off, and dragging and the menu still work on the rows shown. Keys typed into the box never reach the timer or the virtual cube.

All three change only each session's `rank` in `sessionData`, like the ↑/↓ arrows, so the stored data stays csTimer's format. The **Session** dropdown and Alt+↑/↓ session switching follow the same order.

## Import preview and undo

**Export → Import from file** no longer replaces everything straight away. It opens an **Import preview**: one row per session that has solves on either side, with name, puzzle, solve count and date range for **Now** and **File** (a drop is shown in bold, e.g. `1,000 (-1,377)`), totals, and warnings. The warnings cover a file with fewer solves than you have, sessions that Replace all would empty, a slot holding a differently named session in the file, a file whose newest solve is older than yours, and a file without settings. On a phone the table stays inside the dialog.

- **Replace all**: the old behavior; your data becomes the file.
- **Merge**: adds the file's new solves and removes nothing. The preview says how many solves it would add to which sessions; if there is nothing new it changes nothing. The rules are in [MIGRATION.md](MIGRATION.md#replace-all-merge-and-the-safety-net).
- **Cancel** (or a click outside) leaves everything as it was.

Replace all and Merge first download your current data as `jltimer_backup_before_import_….txt`. After the reload a dialog reports what happened and the result of the integrity check (solve counts per session in storage compared with what was written). **Undo import** in that dialog, or in the Export dialog, restores the data from before the import, settings included, until you reload the page.


## Animated background (living themes)

With the **Sakura** (cherry blossom) theme, petals let go of the blossoms in the artwork and drift down in the background: they hang on the branch for a moment, then sway, meander and tumble (a slow spin plus a flip that shows the lighter back of the petal) on a light breeze to the right that now and then picks up a little. They are meant to look like part of the painting, not like real objects: soft, pale versions of the artwork's petal colors, about 33-60% opacity (far petals the faintest), every petal slightly soft and the nearest and farthest ones more blurred. Most are small and far, a few larger and closer. They settle and fade out near the bottom; a few drift in from trees off-screen. About 15-20 are on screen on a computer (up to 28 on a large window) and about 5-10 on a phone.

The petals are part of the background: they pass behind the virtual cube, the timer digits, the scramble, the panels, the button bars and dialogs, and show only faintly through the translucent panels (which blur them).

- **Options → color → Animated background**: *Off*, *On*, or *On, pause while timing* (default). With the default, holding the timer, inspection and the solve itself freeze the petals and fade them out; they fade back in and carry on when the timer is idle again. *On* keeps them falling during solves.
- If the system asks for **reduced motion**, the default is *Off* (you can still turn it on).
- Only themes that bring an animation use it (Sakura for now). Other themes, *None* and *Your images* get no canvas at all.
- **Where the petals start**: the artwork is the page background with `background-size: cover`, centered, so the blossom positions (artwork coordinates of the blossom clusters in the SVG) are mapped to the screen for the current window size. On a phone in portrait the sides of the artwork are cut off, so more petals come from above.

**Performance**: one fixed `<canvas id="jltheme-anim">` behind the panels (`z-index: -1`, `pointer-events: none`), sized by `devicePixelRatio` (at most 2). Petals are pre-drawn sprites (the artwork's own petal path with softened gradients: 3 colors, soft and blurred), drawn with one transform and `drawImage` each. The frame loop uses `requestAnimationFrame` with delta time and runs at 30 fps on phones. Measured script time per frame: desktop p95 0.2 ms (0.4 ms with 4x CPU throttling), iPhone 13 emulation with 4x throttling p95 0.5 ms; no long tasks. Nothing runs while it is paused (timing or a hidden tab): the loop is stopped, not skipped.

**For theme authors**: a theme can add `animate: function(env) { return { frame(dt, env), resize(env), stop() }; }` to its `jlThemes.register({...})` object. `js/themes.js` owns the canvas, the loop, the setting, pausing and reduced motion; `env` has the 2D context, the viewport size, `dpr`, `phone`, and `art(x, y)` to turn artwork coordinates into screen coordinates (types: `JlThemeEnv`, `JlThemeAnimation` in `types/jltimer.d.ts`). The sakura petals are in `js/themes/sakura.js`.

## Your images (custom backgrounds)

Your own pictures work like the built-in enhanced themes: full-strength page background, matching colors, translucent panels. They appear as **Your images** above the built-in themes in **About → Enhanced themes**, and as a compact row under *Enhanced theme* in **Options → color**. The *Enhanced theme* select lists them too, as *Your image: name*.

- **Add**: the **+ Add image** tile opens the file picker (several files at once work; on iPhone it is the normal photo picker). You can also drop image files onto the gallery or paste an image while the gallery is on screen. A new picture is chosen right away and its editor opens.
- **Colors**: on upload jlTimer finds the main colors of the picture (k-means on a 48 px copy) and derives the eight csTimer colors from them: a dark palette for dark pictures, a light one for bright pictures. It then adjusts lightness until text reaches 7:1 against panels, background and buttons, links and PBs 4.5:1 against panels, and the logo text 4.5:1 against its background. Choosing the picture applies these colors as ordinary manual colors, the same way built-in themes do, so you can still tweak them under Options → color; the translucent panels follow your tweaked colors. **Use picture colors** in the editor puts the picture's colors back.
- **Readable panels**: panel opacity is computed per picture, as the lowest value (from 50%) at which the text and link colors stay at 4.5:1 or more over every large color area of the picture, with the dim/brighten setting applied.
- **Edit** on a tile opens the editor: name, **fit** (cover, contain, tile), **focus** point (tap or drag on the preview, or the 3×3 picker), **blur** 0–20 px and **dim / brighten** −60…+60%. The preview has the page's shape, and when the picture is the current theme the page changes live. Changes are saved as you go; **Done** closes the editor, **Delete** asks first and then removes the picture (if it was on, the theme goes back to Sakura).
- **Limits**: at most 12 pictures. Pictures with a side over 2560 px are scaled down to 2560 px and stored as WebP (JPEG where the browser cannot write WebP) at quality 0.85; smaller JPEG, PNG, WebP or GIF files up to 1.5 MB are stored unchanged, and other files are re-encoded the same way. Each also gets a ~360 px JPEG thumbnail for the tiles.
- **Performance**: the picture is the background of a fixed layer behind the page (`#jlbg`); blur is a CSS filter on that layer only and the dim/brighten overlay is a second layer. Nothing runs while timing; the styles change only when you choose or adjust a picture or change a color.
- **Only in this browser**: pictures are not part of exports and are not synced. On another browser (or after clearing site data) a saved *Your image* theme falls back to Sakura with Sakura's colors. Imports keep your pictures (see [MIGRATION.md](MIGRATION.md#your-images)).

The older csTimer option **Options → display → background image (faint overlay)** still works as before (a low-opacity picture over the page); its help text points to Your images for a full background.

Code: `js/mybg.js` (gallery, editor, palette, storage), hooks in `js/themes.js`, `#jlbg` / `.jlbg-*` styles in `css/style.css`. The Options row is an internal property `jlBgUi` that only displays the tiles; it never stores a value.
